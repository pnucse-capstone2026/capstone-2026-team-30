# 2. 데이터베이스 접근 기술 및 스키마 관리 도구 선정 (Prisma ORM)

## Status

Accepted

## Context

본 플랫폼은 사용자 정보, 클러스터 접속 설정, 거버넌스 감사 로그 등의 메타데이터를 저장하기 위해 관계형 데이터베이스로 PostgreSQL을 사용합니다. 
이 환경에서 데이터베이스와 연동하는 코드를 작성할 때 다음과 같은 기술적 제약 사항과 요구사항이 존재했습니다.

1. 타입 안전성(Type Safety) 확보:
   * 프론트엔드와 백엔드가 모두 TypeScript를 사용하는 만큼, 데이터베이스의 테이블 구조 및 쿼리 결과물 역시 완전한 정적 타입으로 백엔드 코드에 매핑되어야 합니다
   * 수동으로 데이터베이스 타입 인터페이스를 작성하는 방식은 데이터베이스 스키마 변경 시 싱크가 깨질 위험이 크므로 자동화된 타입 생성이 필요했습니다.

2. 직관적인 데이터 모델링 및 유지보수:
   * 대규모 원시 SQL을 직접 관리하거나 복잡한 데코레이터 기반의 설정 방식보다, 테이블 관계와 필드 정의를 한눈에 파악할 수 있는 단일 스키마 정의 방식이 요구되었습니다
   * 소규모 팀 구조에서 스키마 변경 이력을 쉽고 일관되게 버전 관리(Migration)할 수 있는 도구가 필요했습니다.

3. 개발 생산성 향상:
   * SQL 작성 실수를 컴파일 타임에 잡기 위해 타입 보정이 지원되는 데이터베이스 클라이언트가 유용하며, 다양한 조건 기반 쿼리를 작성할 때 자동 완성을 지원받아 개발 속도를 높일 수 있습니다.

## Decision

1. Prisma ORM 채택:
   * 본 프로젝트의 백엔드 데이터베이스 접근(Data Access) 기술로 Prisma ORM을 단일 채택하여 사용합니다.
2. 스키마 및 마이그레이션 관리 단일화:
   * 데이터 모델 정의는 단 하나의 스키마 정의 파일(schema.prisma)로 일원화합니다.
   * 로컬 개발 단계의 변경 사항은 prisma migrate dev를 통해 데이터베이스에 반영하며, 생성된 마이그레이션 SQL 파일을 Git으로 추적 관리하여 스키마 버전의 정합성을 보장합니다.
3. 타입 안전성 보장 클라이언트 자동 생성:
   * 스키마 변경 시 prisma generate 명령을 통해 @prisma/client 모듈을 실시간으로 컴파일하여 소스 코드 전반의 정적 타입 데이터베이스 접근 객체를 확보합니다.

## Consequences

* 얻을 수 있는 이점:
  * 설계와 코드의 불일치 위험 제거: 마이그레이션 도구와 데이터베이스 클라이언트가 스키마 정의 파일 하나로 묶여 있어, 스키마 변경이 코드 타입 변경으로 바로 컴파일 타임에 강제됩니다.
  * 수동 타입 매핑 공수 제거: 데이터베이스 조인(Join) 결과물이나 다중 선택 데이터 조회 시 복잡한 반환 인터페이스를 개발자가 수동으로 정의할 필요 없이 정밀하게 자동 추론된 타입을 보장받습니다.

* 감수해야 할 제약 사항:
  * 환경 호환성 오버헤드: 내부적으로 Rust 기반 엔진 바이너리를 통해 통신하므로, 베이스 OS 환경의 런타임 호환성을 타게 됩니다. 이는 아키텍처 결정(Slim 이미지 선정 등)을 통해 관리해야 합니다.
  * 고급 SQL 기능 미지원으로 인한 Raw SQL 의존성: 재귀 쿼리(CTE)나 윈도우 함수 등 고급 분석 쿼리를 작성할 때 Prisma API가 완벽히 대응하지 못해 문자열 방식에 의존해야 할 수 있으며, 이 경우 컴파일 타임 타입 검사의 이점을 부분적으로 상실합니다
  * 독자적인 스키마 문법 종속성 (Vendor Lock-in): 자체 DSL인 Prisma Schema Language에 데이터 모델 및 구조가 묶여 있어, 향후 타 ORM 기술이나 타 언어 플랫폼으로 이전하고자 할 때 스키마 마이그레이션 비용이 비교적 높게 발생합니다.
