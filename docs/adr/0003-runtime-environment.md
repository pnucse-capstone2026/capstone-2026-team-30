# 3. 컨테이너 런타임 베이스 이미지 선택 (Slim vs Alpine)

## Status

Accepted

## Context

본 플랫폼 서비스를 클라우드 환경에 빌드 및 배포하기 위한 컨테이너 이미지화(Dockerizing) 작업을 진행해야 합니다. 이 과정에서 도커 이미지의 크기를 줄이고 배포 성능을 개선하며 보안 취약점 면적을 좁히는 것을 중점으로
베이스 이미지를 선정했습니다.

1. Prisma ORM 네이티브 바이너리 호환성:
   * 백엔드 API 서버는 Prisma ORM을 사용하여 데이터베이스와 통신합니다. Prisma는 자바스크립트가 아닌 Rust로 작성된 플랫폼 종속적 쿼리 엔진 바이너리(Query Engine Binary)를 백그라운드에서 직접 실행합니다
   * 이에 따라 컨테이너 베이스 OS 환경의 표준 C 라이브러리가 Prisma 쿼리 엔진 바이너리와 완전한 호환성을 제공해야 합니다.

2. 빌드 생산성 및 트러블슈팅 편의성:
   * 컨테이너 빌드 및 테스트 단계에서 네이티브 모듈 컴파일 문제로 인한 빌드 지연이나 비정상 종료 문제를 최소화해야 합니다
   * 문제 발생 시 런타임 컨테이너 내부를 직접 디버깅할 수 있는 기본적인 쉘(shell) 도구와 디버깅 패키지가 제공되어야 합니다.

## Decision

1. node:22-slim 베이스 이미지 채택:
   * 백엔드(apps/backend/Dockerfile) 및 프론트엔드(apps/frontend/Dockerfile) 컨테이너의 베이스 런타임 이미지로 표준 glibc가 포함된 경량화 이미지인 node:22-slim을 채택합니다
2. 다중 단계 빌드(Multi-stage build) 적용:
   * 개발용 의존성과 컴파일러가 포함된 builder 스테이지와, 실행에 필요한 최소한의 아티팩트만 포함하는 runner 스테이지로 빌드 단계를 분리하여 프로덕션 이미지 크기를 압축합니다
3. Next.js 독립형(Standalone) 기능 활성화:
   * 프론트엔드의 경우 next.config.mjs 설정을 통해 standalone 패키지로 빌드하여 런타임에 필요한 프레임워크 핵심 파일만 추출해 컨테이너에 적재합니다.

## Consequences

* 얻을 수 있는 이점:
  * 원활한 외부 모듈 호환성 보장: slim 이미지는 glibc를 제공하므로, Prisma의 플랫폼 종속적 엔진 파일 및 향후 추가될 다른 C++ 네이티브 자바스크립트 바인딩 라이브러리가 예외나 크래시 없이 안정적으로 구동됩니다.
  * 빌드 복잡성 해소: Alpine 이미지를 선택할 경우 필요한 libc6-compat 패키지의 수동 설치 등 부수적인 오버헤드를 최소화합니다.
  * 편리한 운영 및 디버깅: 기본적인 리눅스 유틸리티 및 apt 패키지 관리자가 제공되므로 컨테이너 내부 환경 점검 및 클러스터 연동 디버깅이 쉽습니다.

* 감수해야 할 제약 사항:
  * 베이스 이미지 용량 증가: 극도로 가벼운 Alpine(약 5MB)에 비해 크기가 30MB 가량 더 큽니다
  * 보안 취약점 면적의 증가: Alpine과 대비할 때 기본 탑재된 패키지가 많으므로 컨테이너 정적 보안 스캔(CVE Scan) 시 상대적으로 노출되는 보안 경계가 넓어집니다.
